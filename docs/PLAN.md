# Stage 1 Plan — Document Q&A Support Agent

## Context
This is a portfolio project for Upwork: an AI support agent that a business could deploy. In Stage 1, users upload PDF, TXT or DOCX files to a workspace, ask questions, and get streamed answers based only on those documents, with clickable citations. Stage 2 (tool calling, embeddable widget) comes later, so Stage 1's design leaves room for it without building it now.

**Decisions**
- **Workspaces, no login.** Each workspace (for example "Acme Dental") has its own documents, Chroma collection and conversations. Stage 2 widget keys will attach to a workspace.
- **Embeddings can be switched with `EMBEDDING_PROVIDER`:** `local` (sentence-transformers `BAAI/bge-small-en-v1.5`, the default: MIT licence, 384 dimensions, 512-token input limit, so chunks are not silently truncated the way they would be with MiniLM's 256) or `openai` (`text-embedding-3-small`). Chat can be switched with `LLM_PROVIDER=openai|anthropic`, and model names come from env vars.
- **Public live demo** plus the repo, so abuse and cost protection are in scope.
- **Chat UX:** streaming answers, saved history with follow-ups, and a citation preview panel. No OCR.
- **Public demo access:** visitors can use a read-only seeded demo workspace and can create their own temporary workspaces, which expire after 24h and have upload caps. Admin-only operations need `ADMIN_API_KEY`.
- **Citation locations by file type:** a PDF cites the **file + page**. A DOCX cites the **file + nearest heading + paragraph range**. A TXT cites the **file + line range**. The UI labels each one honestly.
- **Tooling:** uv for packages and ruff for lint/format. The frontend uses Tailwind + shadcn/ui and TanStack Query.

## Architecture
```
frontend/ (Vite React TS) ──HTTP/SSE──> backend/ (FastAPI)
                                            ├─ SQLite (workspaces, documents, conversations, messages)
                                            ├─ file storage volume (originals, for preview)
                                            ├─ ChromaDB, embedded in the backend (one collection per workspace + embedding model)
                                            └─ LLM provider (OpenAI | Anthropic), Embedder (local | OpenAI)
```
Backend layout: `backend/app/{config.py, main.py, db/, api/routes/, services/{parsers, chunking, embeddings, vectorstore, llm, rag, ingestion}}`, with tests in `backend/tests/`.

Key design points:
- **Provider interfaces** (`Embedder`, `ChatModel` Protocols) each have a `Fake*` implementation, so tests never call paid APIs.
- **The collection name includes the embedding model slug** (`ws_{id}__{model-slug}`, for example `ws_3__bge-small-en-v1-5`). Switching providers then can't mix vector dimensions, and a re-index endpoint rebuilds the collection.
- **Grounding:** retrieved chunks are numbered `[1]..[n]` in the prompt, and the model must cite with `[n]` or reply with a fixed "not found in the documents" answer. A similarity threshold skips the LLM entirely when nothing relevant comes back. Only sources the answer actually cites are returned as citations.
- **Follow-ups:** the last few turns are condensed into a standalone question for retrieval. The full answer is then generated with that history.
- **Streaming:** `POST /workspaces/{id}/conversations/{id}/messages` returns SSE events (`sources`, then `delta`s, then `done` with the cited sources and both message ids, or `error` with a safe message). The frontend reads it with `fetch` + `ReadableStream`, since EventSource can't POST.
- **Ingestion runs in a background task.** Each document's status moves pending → processing → ready/failed. SHA-256 dedup stops the same file being indexed twice in a workspace. Deleting a document also removes its vectors and its file.

### Backend foundation
- [x] **1. Scaffold:** monorepo dirs, `.gitignore`, `.env.example`, uv project, ruff + pytest config, README skeleton, `master`→`main` rename, and `.claude/settings.json`. That file denies Read/Edit of `.env` and `.env.local` at any depth plus the obvious shell reads (this can't cover every possible command), and asks before package installs.
- [x] **2. Config + app:** `pydantic-settings` config, FastAPI app factory, CORS, `/health`, structured logging. Test: health returns OK.
- [x] **3. Database:** SQLAlchemy models (Workspace, Document, Conversation, Message, Citation JSON) on SQLite, and workspace CRUD routes. Tests: CRUD with a temporary DB.

### Ingestion pipeline
- [x] **4. Parsers:** PDF (pypdf, per page), DOCX (python-docx, tracks headings and paragraphs), TXT (encoding detection, line numbers). Each one outputs `Segment(text, location)`. Tests: fixture files for each type, an empty/corrupt file, and an image-only PDF that should give a clear "no text found" error.
- [x] **5. Chunker:** token-aware, 350 tokens by default with 50 overlap (`CHUNK_SIZE_TOKENS`, `CHUNK_OVERLAP_TOKENS`). It takes an injected `count_tokens`; ingestion passes the embedder's own counter (the real bge tokenizer locally), because the cheap 4-characters estimate under-counts codes and digits (a real test hit 828 tokens against a 512 limit). A safety net splits any chunk the counter still rejects, so none is ever oversized. It keeps location metadata and joins page ranges when a chunk crosses a page. Tests: boundaries, overlap, metadata.
- [x] **6. Embedders:** `LocalEmbedder` (bge-small; adds the bge query prefix to queries only), `OpenAIEmbedder` and `FakeEmbedder`, behind a factory, with chunk size/overlap as settings. Tests: the factory, the fake, the local query prefix, the default chunk size fitting the local model's limit (OpenAI, sentence-transformers and the tokenizer are stubbed in the default suite; a `slow`-marked test checks the real bge model and tokenizer). Each embedder exposes `max_tokens` and `count_tokens()`.
- [x] **7. Vector store:** Chroma wrapper behind a `VectorStore` Protocol for add (replaces a document's old chunks), query (cosine similarity clamped to 0..1), delete-by-document and delete-workspace (every model's collection). Collections are `ws_{id}__{slug}`, with the slug hashed if the name would pass Chroma's 63-char limit. Telemetry is off. Tests use `FakeEmbedder` and a temp-dir Chroma client.
- [x] **8. Upload API:** (call `ensure_chunk_fits(embedder, settings.chunk_size_tokens)` at startup/ingestion, and chunk with `count_tokens=embedder.count_tokens`) `POST /workspaces/{id}/documents` (type and size validation), background ingestion, status listing, delete, `GET .../file` for preview, and re-index. Tests: upload → ready → query finds chunks; dedup; delete removes vectors.

### Answering
- [x] **9. LLM providers:** `OpenAIChat`, `AnthropicChat` and `FakeChat`, all with a streaming interface, and env-configurable models. Tests use mocked SDK streams. Closing a stream early closes the provider stream; per-call token usage goes to an `on_usage` callback (for step 18's spend cap); SDK errors map to our `LLM*Error` types; API keys are `SecretStr`.
- [x] **10. RAG service:** question condensing, retrieval + threshold, prompt build, `[n]` citation parsing and mapping. Tests: grounded answer with citations; off-topic question → refusal without an LLM call; citations that don't exist are dropped. Output is an event stream (sources → answer deltas → done with only the cited sources, `refused`, `uncited`). The whole answer call (system, history, sources, question, reserved output) fits `RAG_TOKEN_BUDGET`, trimming history before sources, so a follow-up stays under Groq's free 8K tokens/min. `[n]` markers are stripped from old answers in history, and document text is fenced as data against prompt injection.
- [x] **11. Chat API:** conversation CRUD, SSE `POST /workspaces/{id}/conversations/{id}/messages` (FastAPI's built-in SSE, with keep-alive pings), and saving the user and assistant messages with their citations and `refused`/`uncited`/`incomplete` flags. A client that leaves mid-answer (Stop) gets its partial answer saved as `incomplete`; errors become an `error` event and save nothing; one reply streams per conversation at a time (409, in-process guard: single worker). Token usage is logged per message. Tests: SSE event sequence, persisted history, errors, the 409 guard, and disconnects (service-level and a raw-ASGI hang-up).

### Frontend
- [x] **12. Scaffold:** Vite + TS + Tailwind + shadcn/ui, routing, a typed API client, TanStack Query, and the app shell/layout.
- [x] **13. Workspaces + documents UI:** a documents sidebar beside the (still empty) chat area. Workspace create, rename and delete (with confirmation). Drag-and-drop or file-picker upload of several files, checked in the browser (type, size, empty) against the server's limit from `GET /config`, then uploaded one at a time. There is no byte progress bar (`fetch` can't report one); each file shows waiting/uploading/rejected, then the document's own pending → processing → ready/failed badge. The list polls only while something is pending or processing. Failed documents show their error and a Reindex button; delete asks first. 409/413/415/400 messages from the backend are shown as they are.
- [x] **14. Chat UI:** a conversation list beside the thread (new, select, delete with confirmation), with the conversation in the URL (`/w/:id/c/:convId`). A new chat is created by its first question, so empty conversations don't pile up. Answers stream live and render as markdown (react-markdown + remark-gfm, no raw HTML). `[n]` markers become citation chips, with a source list under each answer, and clicking one shows the cited passage in a popover. Stop keeps the partial answer, shown as "Stopped" (also after a reload). Refused and uncited answers are shown distinctly, and errors (including the 409 "reply already in progress") get a Retry. Sending is disabled while a reply streams or when no document is ready, with the reason shown. The question limit comes from `GET /config` (`max_question_chars`). The thread follows a streaming answer unless the user has scrolled up.

### Ship
- [x] **17. Docker Compose:** two containers, `backend` and `web`. Chroma stays **embedded** in the backend (no separate Chroma service; that saves a container on 2 GB, and the app is single-process anyway).
  - **Backend image:** multi-stage, pinned `python:3.12.16-slim-trixie` by digest, `uv sync --frozen --no-dev` (no reportlab), CPU-only torch (0 nvidia packages), non-root uid 10001 and a `/health` HEALTHCHECK. The bge model and tokenizer are **baked in** (`HF_HOME=/opt/hf`, `HF_HUB_OFFLINE=1`, verified with `--network none`), and demo_data/ ships in the image.
  - **Exactly one uvicorn worker.** SQLite, Chroma, the model lock and the reply guard are in-process.
  - **web:** `npm ci` + build served by nginx-unprivileged. `/api` is proxied with `proxy_buffering off`, and `X-Forwarded-For` is overwritten. Uvicorn trusts it only from the pinned subnet `172.28.0.0/24`, so a client can't spoof its IP for step 18.
  - **Data and secrets:** data lives in the named volume `backend-data` and survives `down`/`up`. Secrets come only from `env_file: backend/.env`.
  - **Memory:** limits are 1200 MB backend / 64 MB web. Measured: backend 233 MB idle, ~600-780 MB with the model loaded and indexing; web ~15 MB. Image sizes: backend 2.81 GB, web 95 MB.
  - **Docs:** the README documents `EMBEDDING_PROVIDER=openai` as the low-memory option. The seed runs with `docker compose exec backend python -m scripts.seed_demo`.
  - **Tests:** `tests/test_docker_config.py` guards all of the above.
- [x] **18. Demo hardening:** everything sits behind `PUBLIC_DEMO` (off by default, so local dev and client deployments are unchanged; docker-compose turns it on).
  - **Ownership without login:** the browser's random `X-Visitor-Id` (stored server-side only as a SHA-256) owns the workspaces and chats it creates. Every workspace route checks it and answers 404 for someone else's items, including the file preview. react-pdf gets the header through `httpHeaders`, and "Open original" fetches a blob into a tab opened inside the click.
  - **Read-only demo workspace:** recognised by an `is_demo` flag instead of its name. A one-time migration flags the old row, and starter questions follow the flag. Visitors get a 403 on upload, delete, rename and reindex, and the UI hides those controls. `ADMIN_API_KEY` (sent by the seed as `X-Admin-Key`, compared in constant time; empty never matches) bypasses this.
  - **Per-IP rate limits:** an in-process sliding window instead of slowapi. slowapi's Retry-After header injection doesn't fit the SSE route, it would add 3 dependencies, and one worker makes memory correct. IPv6 is keyed by /64, and the IP comes only from step 17's trusted proxy setup. Limits cover chat (minute and day), uploads, new chats and new workspaces (3 per IP per 24 h). Over a limit the API returns 429 with Retry-After and a readable wait.
  - **Daily token cap:** `DAILY_TOKEN_CAP=150000` (Groq free: 200K/day), counted per UTC day in SQLite, so it survives restarts. It is checked before a question, and a refused question makes no LLM call. Groq's own 429 was already friendly (step 9).
  - **Caps:** documents per workspace, total visitor storage (507), and a per-document **chunk** cap instead of pages (it covers TXT and DOCX too, and it's checked before embedding).
  - **24 h expiry:** visitor workspaces and visitors' demo chats expire, swept by one asyncio task in the single worker. Expired items are already 404 before the sweep.
  - Additive `ALTER TABLE` migration for the existing Docker volume. The hard size cap still lives in the proxy (nginx `client_max_body_size`, and Caddy in step 21).
- [x] **19. Quality evidence:** `backend/eval/` holds 34 golden questions in `golden.toml`: answerable ones (half paraphrased the way patients type), follow-ups, off-topic and in-domain unanswerables, and 2 each in Arabic, Spanish and French. It runs in-process, with no server or PUBLIC_DEMO caps, and each run is saved to `eval/results/` and compared with the previous one. The README has the results.
  - **Retrieval eval** (`uv run python -m eval.retrieval`, free): hit@1/3/6 by group, and the score distribution. Paraphrased hit@1 is 50% vs 88% literal; hit@6 is 100% for all English questions. Non-English hit@6 is 50-100%.
  - **Answer eval** (`uv run python -m eval.answers [--run]`): estimates tokens first (dry run by default, hard stop at 50K), then asks 8 questions 60 s apart, scored by plain checks. First run on gpt-oss-120b: 8/8 (facts, cited section, refusals), 9,185 tokens.
  - **`RAG_MIN_SCORE` kept at 0.45** (re-checked on section chunks). English answerable questions score ≥ 0.559 and off-topic ones ≤ 0.461, so 0.51 would split the gap. But that margin rests on only 4 off-topic questions, and 0.51 refuses 4 of 6 non-English questions before the LLM (2 of them retrievable). An off-topic question that slips through costs one LLM call and is still refused (the weather question did). The reasoning is recorded in `config.py`, `.env.example` and the README.
  - **PDF bold headings:** headings set bold at body size were missed, and the document fell back to token windows. They are now detected (all-bold short lines that aren't sentences, when the body isn't bold).
  - Not done: the Anthropic run (same command with `LLM_PROVIDER=anthropic`), and multilingual embeddings (gap measured; options are in the README).
  - [x] **Section-aware chunking** (pulled forward before the demo recording): the chunker keeps each section together (PDF headings found by font size, DOCX headings with their paragraphs and table rows, TXT `Q:` pairs and `#` headings) and only splits a section into token windows when it is over the limit. Locations name the section heading and the tightest page, paragraph or line range ("4. Payments and refunds · page 2"). The demo docs now index as 21 chunks (7 + 3 + 11) instead of one per file. Citations are also renumbered 1, 2, 3 in order of first use for display, and gpt-oss's narrow no-break space becomes U+00A0 instead of a plain space.

The full git history was scanned for secrets (see below).

- [ ] **21. Deploy (deferred):** no live hosting for now; the portfolio is the GitHub repo plus a demo video. The noreply email and history rewrite are already done.
